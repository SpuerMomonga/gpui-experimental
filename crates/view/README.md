# view

## Purpose

`view` manages feature-view mounting, state, and hosting. A view can be mounted in
`workspace` or in an independent GPUI window. Callers use `ViewHandle` to access the entity
and optional window handle created for a mount, and use its `View` controller to manage the
lifecycle. `ViewId` is the logical identity generated by `ViewStore` for each mount; no
additional feature or window key is introduced.

The Rust code is still a scaffold, and `ViewStore` does not yet persist entities, create
windows, or emit events. The API below describes the boundaries the implementation must
preserve; concrete fields follow the GPUI version pinned in `Cargo.lock`.

## GPUI Boundary

GPUI window roots must implement `Render`, while `ViewDelegate::render_view` is a feature
interface from this crate, not a root that GPUI recognizes directly. An independent window
is therefore hosted by an internal `ViewRoot<V>` adapter. The adapter holds `Entity<V>`,
implements `Render`, and forwards `render` to `ViewDelegate::render_view`. It only connects
the two interfaces; it does not reimplement type erasure for `AnyView` or `WindowHandle`.

The `App::open_window` builder receives `(&mut Window, &mut App)` and must return an entity
that implements `Render`. `WindowHandle<V>` is only a window reference and does not keep the
window alive. Call `Window::remove_window` to unload an independent window; after GPUI
actually removes it, `App::on_window_closed` maps its `WindowId` back to the `ViewId`. GPUI's
close callback does not provide the closed `Window`, so `View`/`ViewStore` own the window
lifecycle rather than passing window borrows through delegate callbacks.

## View Options

`ViewOptions` supports three configurations: workspace, detachable view, and direct window.
`WindowOptions` is used only to create a GPUI window and does not carry logical view identity.

```rust
use gpui::{SharedString, WindowOptions};

pub struct ViewConfig {
    /// Title shown when mounted in the workspace.
    pub title: SharedString,
    pub searchable: bool,
    /// Whether this is the workspace's default view.
    pub default: bool,
}

pub struct DetachableConfig {
    /// Title shared by the workspace and independent window.
    pub title: SharedString,
    pub searchable: bool,
    /// GPUI configuration used when the view is placed in an independent window.
    pub window: WindowOptions,
}

pub enum ViewOptions {
    /// Mount only in the workspace.
    View(ViewConfig),
    /// Can move between the workspace and an independent window.
    Detachable(DetachableConfig),
    /// Create an independent window directly; GPUI configuration controls its behavior.
    Window(WindowOptions),
}
```

Every `mount` creates a new `ViewId`. For a singleton, the feature module should retain and
reuse its `ViewHandle` instead of adding another key to `ViewOptions`; multiple instances
then remain collision-free.

## Lifecycle and API

The Rust API uses `mount` and `unmount` to represent a view entering and leaving
`ViewStore`; both operations belong to the `View`/`ViewStore` lifecycle-control layer.
`ViewDelegate` declares no lifecycle callbacks; cross-crate events use `Mounted` and
`Unmounted`. Unmounting simply means that the view has left the store and does not encode
whether a window closed, a replacement occurred, or a caller requested removal.

```rust
use gpui::{AnyWindowHandle, App, Context, Entity, IntoElement, SharedString, Window};

pub struct ViewHandle<V> {
    pub id: ViewId,
    pub view: View,
    pub entity: Entity<V>,
    pub window: Option<AnyWindowHandle>,
}

pub struct View {
    // The view owns lifecycle hooks and a deferred removal request.
}

impl View {
    pub fn on_mount(&self, callback: impl FnOnce(&mut App) + 'static) {}
    pub fn on_unmount(&self, callback: impl FnOnce(&mut App) + 'static) {}
    pub fn remove_view(&self) {}
}

pub trait ViewDelegate: 'static + Sized {
    fn render_view(&mut self, view: &mut View, window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement;

    fn placeholder_text(&self, _view: &mut View, _window: &Window, _cx: &App) -> Option<SharedString> {
        None
    }

    fn render_search_control(&mut self, _view: &mut View, _window: &mut Window, _cx: &mut Context<Self>) -> Option<impl IntoElement> {
        None
    }

    /// Called whenever the query changes; receives an empty string when the input is cleared.
    fn perform_search(&mut self, _query: &str, _view: &mut View, _window: &mut Window, _cx: &mut Context<Self>) {}

    fn actions(&mut self, _view: &mut View, _window: &mut Window, _cx: &mut Context<Self>) -> Vec<ViewAction> {
        Vec::new()
    }

    fn primary_action(&mut self, _view: &mut View, _window: &mut Window, _cx: &mut Context<Self>) -> Option<ViewAction> {
        None
    }
}

pub trait ViewContext {
    fn open_view<V: ViewDelegate>(
        &mut self,
        options: ViewOptions,
        build: impl FnOnce(&mut App, View) -> Entity<V>,
    ) -> anyhow::Result<ViewHandle<V>>;
}
```

Keep `impl IntoElement` for `render_view` and `render_search_control`. Callers hold a concrete
`Entity<V>` and can return their own GPUI element type; call `into_any_element()` only when
an adapter combines heterogeneous elements in a shared container. `placeholder_text` only
reads state, so it uses immutable `Window` and `App` references.

`ViewDelegate` does not declare `mount` or `unmount` methods; every other callback receives
`view: &mut View` for removal requests and access to the current mount's control state.
Lifecycle hooks themselves are registered in the `open_view` build closure. `View` is not a
GPUI render entity and needs no custom context wrapper.

`View` does not contain a `gpui::Window` and provides no API to reborrow one from the
controller. A GPUI window is available only temporarily as the `window: &mut Window`
parameter of a `ViewDelegate` callback; window handles are managed by `ViewStore`/
`ViewHandle`.

`search` is the sole synchronization point between search input and view state. `workspace`
owns the input's current string, updates its `query` in the input handler, and then passes
the same `&str` to the active view entity. A view that searches asynchronously should retain
its query version and call `Context::notify()` to refresh its results. `render_search_control`
only renders supplemental controls on the right side of the search bar; it does not read the
query value.

`View` represents the current mount instance, not a GPUI render entity. The `open_view` build
closure receives this object, so a feature view can register lifecycle callbacks while it
is being built:

```rust
fn open_clipboard(cx: &mut App) -> anyhow::Result<ViewHandle<ClipboardView>> {
    cx.open_view(ViewOptions::View(ViewConfig {
        title: "Clipboard History".into(),
        default: true,
    }), |cx, view| {
        view.on_mount(|cx| {
            // Acquire view-owned resources.
            let _ = cx;
        });
        view.on_unmount(|cx| {
            // Release view-owned resources here.
            let _ = cx;
        });
        cx.new(|_| ClipboardView)
    })
}

struct ClipboardView;
```

Call `view.on_mount(|cx| {})` and `view.on_unmount(|cx| {})` in the `open_view` build closure.
`ViewStore` invokes them during mount and unmount, passing the current `&mut App`. Render,
search, and action callbacks on `ViewDelegate` all receive `&mut View`, so they can call
`view.remove_view()` directly. `remove_view()` records one deferred removal request;
`ViewStore` reads and clears it after the current GPUI borrow ends, then runs the unified
unmount flow.

For example, a view action callback can request closure as follows:

```rust
fn primary_action(
    &mut self,
    view: &mut View,
    _window: &mut Window,
    _cx: &mut Context<Self>,
) -> Option<ViewAction> {
    view.remove_view();
    None
}
```

`ViewStore` keeps its own copy of the same `View`: it runs registered mount callbacks during
mount and unmount callbacks during unmount, passing the current `&mut App` to both. The
`AnyWindowHandle` for an independent window is stored by `ViewStore` and `ViewHandle`, not by
the `View` controller. The store also handles `remove_view()` requests after the GPUI borrow
ends. Lifecycle driving is an internal store responsibility, not re-exposed as
`ViewDelegate::mount` or `ViewDelegate::unmount`; ordinary view callbacks still receive
`&mut View`.

## GPUI Actions

Actions use GPUI's built-in `Action` rather than defining a second protocol based on command
IDs. A `Vec<ViewAction>` must hold multiple concrete action types, so type erasure happens
inside `ViewAction`; callers pass a concrete action to its generic constructor and never
write the `Box` themselves.

```rust
use gpui::{actions, SharedString};

actions!(clipboard, [ClearHistory]);

pub struct ViewAction {
    pub title: SharedString,
    pub icon: Option<SharedString>,
    action: Box<dyn gpui::Action>,
}

impl ViewAction {
    pub fn new<A: gpui::Action>(title: impl Into<SharedString>, action: A) -> Self {
        Self {
            title: title.into(),
            icon: None,
            action: Box::new(action),
        }
    }

    pub fn action(&self) -> &dyn gpui::Action {
        self.action.as_ref()
    }
}
```

When `workspace` renders a button, it calls
`window.dispatch_action(action.action().boxed_clone(), cx)`. Keyboard shortcuts and buttons
therefore enter the same GPUI dispatch tree and are handled by `Window::on_action`, element
`.on_action`, or `App::on_action`. `title` and `icon` describe only the action-bar display;
the GPUI `Action` still owns the action name, parameters, and keymap registration.

## ViewStore and Events

`ViewStore` uses `SlotMap<ViewId, ViewEntry>` to keep each mount's `View` controller,
metadata, `AnyEntity`, and optional `AnyWindowHandle`. `ViewEntry` does not contain an empty
`Box<View>`; GPUI's `AnyEntity` erases entity types, and `AnyWindowHandle` erases window
types.

```rust
pub enum ViewEvent {
    Mounted { id: ViewId },
    Changed { id: ViewId },
    Unmounted { id: ViewId },
}

impl gpui::EventEmitter<ViewEvent> for ViewStore {}
```

The mount flow creates the entity and any required window before storing the entry and
emitting `Mounted`. If window creation fails, roll back the entry and emit no partial event.
The unmount flow first removes visible state from the store and then emits `Unmounted` once;
GPUI's window-close callback must enter this path only once. Use `cx.notify()` for ordinary
field changes and the events above for cross-crate semantic changes.

## Example

```rust
use gpui::{App, Context, IntoElement, SharedString, Window};

fn open_clipboard(cx: &mut App) -> anyhow::Result<ViewHandle<ClipboardView>> {
    cx.open_view(
        ViewOptions::View(ViewConfig {
            title: "Clipboard History".into(),
            default: true,
        }),
        |cx, _view| cx.new(|_| ClipboardView {
            query: String::new(),
        }),
    )
}

struct ClipboardView {
    query: String,
}

impl ViewDelegate for ClipboardView {
    fn render_view(
        &mut self,
        _view: &mut View,
        _window: &mut Window,
        _cx: &mut Context<Self>,
    ) -> impl IntoElement {
        gpui::div()
    }

    fn placeholder_text(
        &self,
        _view: &mut View,
        _window: &Window,
        _cx: &App,
    ) -> Option<SharedString> {
        Some("Search clipboard history".into())
    }

    fn perform_search(
        &mut self,
        query: &str,
        _view: &mut View,
        _window: &mut Window,
        cx: &mut Context<Self>,
    ) {
        self.query.clear();
        self.query.push_str(query);
        cx.notify();
    }
}
```
